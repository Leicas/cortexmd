# Bounded read-only workers

CortexMD can delegate a scoped investigation to an explicitly configured smaller model. The model iteratively uses a restricted set of code or note tools and returns a compact answer with runtime-assigned evidence references. It does not need Portal, AiKA, or any workflow catalog.

Workers are disabled by default. Normal search and navigation remain available without a model provider. This feature does not upload your local checkout, edit files, reindex repositories, or save generated answers as memories.

## Configure the server

Use a tool-calling chat-completions-compatible endpoint. Configure an exact endpoint URL, not a provider base URL. A server administrator chooses the model and destination; callers cannot override either. Provider credentials stay on the server and are separate from reranker credentials.

```dotenv
WORKER_ENABLED=true
WORKER_PROVIDER=openai-compatible
WORKER_ENDPOINT=https://your-provider.example/v1/chat/completions
WORKER_MODEL=your-tool-capable-small-model
WORKER_API_KEY=your-provider-key
```

Selected source and note content is sent to that configured provider. Configure a destination appropriate for the data. The adapter performs no automatic model escalation or retry. Endpoint protocol compatibility is required; support for a provider's other APIs is not implied.

| Setting | Default | Meaning |
| --- | --- | --- |
| `WORKER_MAX_CONCURRENCY` | 2 | Active investigations; excess requests fail rather than queue indefinitely |
| `WORKER_MAX_TOOL_CALLS` | 12 | Tool calls per investigation |
| `WORKER_MAX_ROUNDS` | 8 | Model invocations per investigation |
| `WORKER_MAX_INPUT_TOKENS` | 100000 | Cumulative conservative input admission budget |
| `WORKER_MAX_OUTPUT_TOKENS` | 4000 | Cumulative output budget |
| `WORKER_MAX_TOOL_RESULT_BYTES` | 16000 | Maximum individual tool result |
| `WORKER_TIMEOUT_MS` | 90000 | Investigation deadline |

Input admission uses a conservative UTF-8-byte estimate of the repeated transcript and tool schemas, plus framing overhead. It is not tokenizer-accurate billing. Provider-reported usage and estimates are separate in the response. Without provider usage, output accounting is conservative too. Limits are positive integers; a request can lower configured limits, never raise them.

Cancellation and deadlines interrupt asynchronous provider requests and are checked between retrieval operations. Synchronous SQLite queries cannot be preempted while running on the Node event loop; the deadline is not a hard process-isolation guarantee. Query result counts and file reads are bounded separately.

## Invoke

MCP tool `worker_run`:

```json
{
  "task": "Trace how authentication errors reach MCP clients",
  "mode": "code-investigator",
  "repo": "example",
  "paths": ["src/auth", "src/server"],
  "budget": { "maxToolCalls": 8, "timeoutMs": 60000 }
}
```

Code mode requires a registered repository slug. Omitted `paths` means that repository; narrower paths are preferable. Knowledge mode requires explicit `note_paths` and accepts neither `repo` nor code `paths`:

```json
{
  "task": "Which decisions explain the current retry policy?",
  "mode": "knowledge-investigator",
  "note_paths": ["Projects/example"]
}
```

The CLI uses the existing configured CortexMD server and credentials:

```sh
cortexmd ask --repo example --path src --question "How are retries bounded?"
cortexmd ask --mode knowledge-investigator --note-path Projects/example --question "Why this retry policy?"
```

CLI output is JSON. An incomplete, cancelled, or failed investigation exits nonzero after printing any structured result; automation must not treat partial coverage as success.

## Scope and evidence

The code worker can search symbols, read file outlines and verified symbol bodies, and follow scoped callers/callees. The knowledge worker can lexically search and read scoped notes. It cannot invoke arbitrary MCP tools, shell commands, writes, maintenance operations, or another worker.

Every tool call enforces the fixed scope. The worker shares the existing server authentication/access boundary: these path restrictions narrow a request; they are not a new tenant or per-user repository authorization system. The caller's ordinary server access must already be appropriate.

Results include `status`, `answer`, cited `findings`, `evidence`, `coverage`, and `usage`. Evidence IDs are generated by the runtime; unsupported citations are rejected. Source references carry paths and available hashes/ranges. These checks establish traceability, not that the model interpreted the source correctly.

Code metadata comes from the index. Source bodies require a local server checkout whose normalized content hash matches the indexed file. A repository registered on another machine does not make its files readable here. Missing or stale bodies, truncation, and exhausted budgets are disclosed. Recheck exact source and local modifications before editing or making a final review decision.

## Validation and rollout

Run the server build and worker runtime/provider/tool tests. Provider transport tests use a local HTTP fixture and do not prove quality or access for an external model. Before enabling routine use, evaluate a configured model on cross-file explanations, test coverage investigations, and note-grounded decisions. Compare against direct CortexMD retrieval on correctness, supported citations, main-agent context, total provider usage, latency, and retries.

Local snapshot upload, generated patches, persistent answer caching, and automatic memory writes are outside this release. The two modes are deliberately bounded read-only investigators.
